What the WordPress connector needs from the Public API

The connector is being built against the API as it stands today — no work is blocked. Two gaps change what it can promise a customer, and one of them decides whether the plugin can ever be handed to someone outside AIVIS.

Section 01

How the connector uses the API

Three call patterns, on three different clocks. The one that matters most for capacity planning is the third: rendering a page makes no API call at all. The plugin serves structured data from a local table, so your API sits on the sync path, never on a visitor's critical path — an AIVIS outage costs freshness, not uptime.

Section 02

What one token reaches today

The plugin has to keep its token in the site's database. That database is copied into every backup, every staging clone and every migration, and is readable by anyone with admin access to the site or its host. So the question "what does one leaked token expose?" is not hypothetical — it is the ordinary lifecycle of a WordPress install.

Section 03

The two 404s, and why we read your error strings

A withdrawn artifact and an artifact that has not been generated yet both return 404. Your route already tells them apart — and that distinction is load-bearing, because the two demand opposite responses. Right now we get it by matching the English message, which means a copy edit on your side silently changes plugin behaviour on customer sites.

Section 04

The requirements

API-1
Blocker

Business-scoped read-only tokens

Current behaviour
ApiToken carries only userId — no scope, no expiry, no revokedAt. requireApiToken() resolves a token to a user and every route scopes by it: chain: { business: { userId: auth.userId } }.
Why it matters
One token in one customer's WordPress database grants read access to every business on the account. An agency account with thirty clients exposes all thirty through any one of them. Until this changes, the connector cannot ship to installs we do not control.
Proposed contract
A nullable ApiToken.businessId — null preserves today's behaviour for existing tokens. When set, every endpoint resolves only within that business and 404s outside it, exactly as it already does for another user's data. Permission flags jsonld:read and events:write, as the edge connector's V-02 already specified. GET /me reports the binding so an integration can show what its token reaches.
Unlocks
Customer-managed installs, and any path to WordPress.org distribution.
API-2
High

An explicit retraction signal

Current behaviour
No suppressedAt, publication state or tombstone. UrlJsonLdArtifact has staleAt, which means "inputs changed, regenerate" — not "withdrawn". Withdrawal today is a hard delete of the Url row, cascading to the artifact and leaving no trace.
Why it matters
Retraction is the operation with real consequences: a wrong price, an incorrect claim, a stale offer already ingested by AI crawlers. "Publish a correction" is not equivalent — the customer needs the block gone. We infer withdrawal from two signals today, and worst-case latency is a full sync interval.
Proposed contract
UrlJsonLdArtifact.suppressedAt, set by a per-URL Unpublish action plus a chain-level bulk action — reversible, and it keeps the audit trail the hard delete destroys. While suppressed, the lookup returns 410 Gone, and the inventory row reports it so a sync pass sees it without a per-URL fetch. 
GET /api/public/v1/jsonld?url=…
410 Gone
{ "error": { "code": "withdrawn",
             "message": "This artifact was unpublished",
             "suppressedAt": "2026-09-05T11:20:00.000Z" } }
Unlocks
Immediate withdrawal instead of inference. Without it, every consumer builds the same two-signal guess, and each gets it slightly wrong.
API-3
High

A stable machine-readable error code

Current behaviour
The route already separates the two 404 causes — but only as prose in {"error":{"message":…}}, and the published OpenAPI description flattens both into one line: "URL not found in your businesses, or JSON-LD not generated yet."
Why it matters
We string-match your message to decide whether to pull structured data off a live page. It works, and it is the right distinction — it is just carried by something neither side treats as a contract.
Proposed contract
A code beside the message, versioned with the API while messages stay free to change. Initial vocabulary: url_not_found, jsonld_not_generated, withdrawn, invalid_token, account_deactivated, bad_request.
Unlocks
Makes the retraction fast path contractual instead of fragile. Cheapest item in this document.
API-4
Medium

Conditional requests

Current behaviour
No ETag, Last-Modified or Cache-Control on any endpoint. Every poll transfers a full payload.
Why it matters
A 3,000-URL site re-reads its entire inventory every fifteen minutes, forever, to discover that nothing changed. That is the bulk of the traffic in the table in Section 01, and it scales with catalogue size rather than with change rate.
Proposed contract
ETag on the artifact endpoints — the artifact's updatedAt plus a payload hash is sufficient — honouring If-None-Match with 304. On list endpoints, a per-page ETag keyed on the newest updatedAt in that page.
Unlocks
A 5-minute freshness target that stays affordable at scale.
API-5
Medium

Per-URL inventory lookup

Current behaviour
Inventory state — jsonLd.ready, jsonLd.stale, captureStatus — is reachable only by paginating an entire chain.
Why it matters
The "Refresh this page now" button in the WordPress admin is an O(1) question that currently costs an O(chain) walk.
Proposed contract
A ?url= filter on /chains/{id}/urls, or the inventory fields on a GET /urls/{id} response.
Unlocks
Single-URL freshness checks, and a much faster confirmation step for retraction.
API-6
Medium

A change feed

Current behaviour
No way to ask what changed since a given point. Sync is a full inventory walk every interval.
Why it matters
Polling sets the floor on how fast a correction reaches a live page. On WordPress there is no CDN purge hook to piggyback on, so this is the only lever that moves retraction latency below the sync interval.
Proposed contract
In ascending order of effort: an updatedSince parameter on /chains/{id}/urls; or the HMAC-signed outbound refresh ping already sketched as the edge connector's V-03, calling a consumer-registered endpoint after a generate or a retract.
Unlocks
Near-real-time sync; drops the polling floor for every consumer.
API-7
Low

Documented rate limits

Current behaviour
No rate limiting exists in the codebase and none is documented.
Why it matters
We self-throttle to twenty artifact requests per job — a number chosen to be obviously polite, not because it matches anything real. If it is too conservative we are needlessly slow; if it is too aggressive nobody finds out until it hurts.
Proposed contract
Document the intended per-token limits. When limits arrive, return 429 with Retry-After — already implemented defensively on our side, so it will be honoured the day it appears.
Unlocks
A real budget to design against.
API-9
Medium

Connector status report

Current behaviour
AIVIS has no visibility into connected sites — whether they sync, which version they run, whether purges confirm, and whether other plugins are also emitting structured data on the same pages. ApiToken.lastUsedAt is the only signal.
Why it matters
AIVIS is meant to be the primary source of structured data. The connector now detects Yoast, Rank Math and friends emitting their own Organization and WebSite nodes next to ours and flags it red — never altering them — but that finding is only useful if it reaches the people who own the customer relationship.
Proposed contract
POST /businesses/{businessId}/connector-status → 202, sent after each authoritative sync and whenever the conflict set changes. Carries plugin version, site host, sync counts, cache state and the conflicts found — nothing about people. Opt-out in the plugin. 
{ "connector": "aivis-os", "version": "1.0.0", "site": "example.com",
  "sync": { "authoritative": true, "counts": { "active": 312, "suspended": 0, … } },
  "cache": { "adapter": "wp-super-cache", "lastPurge": "confirmed" },
  "conflicts": { "activePlugins": ["yoast"],
                 "items": [ { "url": "https://example.com/", "sources": ["yoast"],
                              "types": ["Organization", "WebSite"] } ] } }
Unlocks
A connected-sites view per business, and the conversation with a customer whose SEO plugin is fighting AIVIS for the same node. The connector already sends it; a 404 backs off for a day.
API-8
Filed, not requested

Host-level URL equivalence

Current behaviour
lib/public-api/lookup.ts matches exact plus a trailing-slash variant, and says why: "Anything beyond that (scheme swaps, host case, query strings) stays an exact-match miss on purpose — silently matching the wrong page would be worse than a 404."
Our position
We think that judgement is right, and this entry exists so the decision is on the record rather than rediscovered later. The edge connector's V-07 asked for full server-side normalization; on reflection the failure it prevents — a missing block — is far safer than the one it introduces.
The one narrow ask
Host-level www equivalence only, resolved against the business's own baseUrl. That is the single variant that arises from ordinary WordPress configuration rather than from a genuinely different page. Scheme, case and query handling should stay strict.
Unlocks
Removes the last class of silent misses that is not the site's own fault.

Section 05

What we do until then

So it is clear what is being worked around rather than waited on. Nothing in this list blocks the connector from being built or from working.

GapInterim behaviour
API-1v1 restricted to AIVIS-controlled installs. Token preferentially in wp-config.php, not the database. Mandatory businessId equality on every artifact, plus chainId membership when inventory context exists.
API-2Withdrawal inferred from the 404 body plus an authoritative inventory pass. Worst-case latency: one sync interval.
API-3Defensive string match on the 404 message, conservative fallback on anything unrecognised.
API-4Full-payload polling at a 15-minute default.
API-5Chain walk for a single-URL refresh.
API-6Interval polling only.
API-7Self-imposed cap of 20 artifact requests per job.
API-8Outbound lookups send the permalink unmodified; normalization applies only to our local index key.

Section 06

Machine-readable

This page carries its own data. Two embedded blocks describe it to a parser: a schema.org TechArticle in JSON-LD, and a typed requirements list under #api-requirements-data. Every requirement section also carries stable id, data-requirement and data-priority attributes, so document.querySelectorAll('[data-priority="blocker"]') is a valid way to read this document.

const doc  = document.getElementById('api-requirements-data');
const reqs = JSON.parse(doc.textContent).requirements;
reqs.filter(r => r.priority === 'blocker');   // [ { id: "API-1", … } ]
The same requirements are maintained as Markdown in docs/API-REQUIREMENTS.md in the connector repository, and the call sequences above are on the program map board alongside the sync loop and retraction tree. This page is the version meant to be handed over.
